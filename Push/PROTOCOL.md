# Botto push protocol v1

Protocol v1 uses plugin `botto-push`, encrypted
payload key `botto`, and AES-GCM additional data prefix `botto-push:v1`.

This is the shared contract for the native client, Hermes plugin, and relay.
See [notification setup](../docs/push-notifications.md) for host and deployment requirements.
Cloudflare is the first relay adapter. No deployment or live delivery is implied
by this contract.

## Identities and authentication

The plugin creates and retains a random 32-byte installation token on its host.
`installation_id` is the lowercase SHA-256 hexadecimal digest of that token's
64-character lowercase hexadecimal encoding. The relay verifies every request
using `Authorization: Bearer <installation_token>` and the digest in the path.
This authenticates an accountless installation without a separate provisioning
secret. Never put capabilities in URLs or logs. The native client never receives
the installation token; it manages pairing through the authenticated Hermes
connection. The relay never receives Hermes credentials or preview keys.

`device_id` is a lowercase UUID without hyphens, randomly generated by Botto.
`generation` is a positive integer persisted and increased by the plugin when
the target, key, or preferences change, or on removal. Identical retries and
visibility-only updates retain it. The relay retains
the last generation and rejects older writes. A removal is a tombstone; a
delayed old registration must not restore a removed device. A later deliberate
pairing uses a fresh random device ID and key. Device-token rotation for a still
authorized pairing advances its generation; Botto persists the returned value.

`event_id` and `thread_id` are opaque lowercase hexadecimal HMAC-SHA256 digests
generated by the plugin from host-owned event and canonical chat identities.
`request_id` is an optional opaque digest for cancellation of waiting prompts.
Raw profile/chat/request names and canonical routing IDs belong inside the
encrypted preview. Event kinds are `reply`, `approval`, `question`, `failure`.
Times are integral Unix seconds. Absolute expiry is checked on every read/send.

## Authenticated host enrollment lifecycle

Configured automatic installation uses the host's explicit-profile
`POST /api/dashboard/agent-plugins/install-profile` contract with existing host
authentication, a body `profile`, immutable source/ref, and `force: false`.
Botto requires a successful acknowledgment naming the same exact profile.
Hosts without this proposed endpoint use explicit-profile manual setup; Botto
never retries the legacy launch-profile installer. No relay credential is
needed for installation.

Botto submits enrollment through its verified, profile-scoped Hermes connection.
It retires push dispatch before replacing that connection; saved pairing keys
remain available for verified tap routing and a later return to the saved host.

An enrollment includes `expected_generation`: zero for a fresh device ID, or
the last acknowledged generation for an update. Expiring operation receipts
cannot authorize changing a newer device generation. Exact retries may confirm
matching current state without mutation. Owner removal permanently retires the
device ID, including removal before its first enrollment arrives. Re-enabling
uses a new random device ID and key.

Host status returns bounded lifecycle metadata, including completed removals.
Each device has `state`: `active`, `pending`, `rejected`, `relay_retired`, or
`removed`. Relay retirement preserves the owner's pairing authorization but
does not confirm working delivery. Ordinary resume with the same token cannot
revive it. A verified token change with the expected generation may recover a
relay-retired target; an owner-removed ID cannot recover automatically.

## Relay HTTP interface

All bodies are JSON objects with `v: 1`; reject unknown fields, malformed
identities, oversized bodies, non-finite times, and unsupported versions. Every
response is JSON with `Cache-Control: no-store`. Write bodies are at most 32 KiB.
Request credentials are scoped by installation, and accepted bundle IDs are an
operator-configured allowlist. Sandbox and production are distinct targets.

### Register or update a device

`PUT /v1/installations/{installation_id}/devices/{device_id}`

```json
{
  "v": 1,
  "generation": 1,
  "token": "lowercase APNs token hex",
  "bundle_id": "com.sree.botto",
  "environment": "sandbox",
  "preferences": {"replies": true, "requests": true, "failures": true, "previews": true},
  "visible_chat": null,
  "visible_until": 0
}
```

`visible_chat` is null or the opaque `thread_id`; leases are capped at 90 seconds
from relay receipt. Clear visibility on background/disconnect when possible;
expiry is authoritative. Identical generation and identical contents are
idempotent. Identical generation with different contents is a conflict. A newer
generation replaces the record atomically. Preferences apply at send time.
Only `accepted` or `duplicate` confirms registration. A `revoked` or `stale`
registration/presence response cannot confirm an active target. The plugin
retires that target locally and stops encrypting new events for its generation;
host recovery may advance a relay-retired target only for a changed token with
the expected generation. Owner-removed pairings require fresh device IDs and
keys. Event diagnostics preserve `invalid_target` and `permanent_failure`.

### Renew device visibility

`POST /v1/installations/{installation_id}/devices/{device_id}/presence`

Body: `{"v":1,"generation":1,"revision":1,"visible_chat":null,"visible_until":0}`.
This updates only visibility for the exact active generation; stale or revoked
generations cannot renew. Non-null leases are capped at 90 seconds from receipt.
The plugin persists an increasing presence revision; older revisions are stale,
and equal revisions must have identical contents to be idempotent. A new
registration generation resets its relay presence revision to zero.
It does not increase the registration generation or invalidate queued events.
The plugin uses this route when an enrollment request changes only visibility.
Client visibility changes are serialized; a later clear must follow an earlier
renewal rather than racing it. Other enrollment changes still increase the
generation. The plugin derives the opaque visible chat from authenticated
profile/root/stored coordinates and never forwards raw routing IDs.

### Remove a device

`POST /v1/installations/{installation_id}/devices/{device_id}/revoke`

Body: `{"v":1,"generation":2}`. Persist the tombstone and cancel queued work.
Return only after any already-started send has settled or been classified as
ambiguous. No new send for that revoked generation may start after the response.
Already-submitted APNs messages may still arrive. Repeating removal is safe.

### Submit an encrypted event

`POST /v1/installations/{installation_id}/events`

```json
{
  "v": 1,
  "event_id": "opaque event hex",
  "thread_id": "opaque chat hex",
  "kind": "reply",
  "request_id": null,
  "created_at": 1800000000,
  "expires_at": 1800003600,
  "targets": [{"device_id":"device UUID hex","generation":1,"sealed":"base64 combined AES-GCM box"}]
}
```

The plugin supplies at most 32 targets, each with ciphertext for that device's
own key and current generation. The relay must never substitute a new generation
for an old event target. Receipt identity is installation/event/device/generation.
Enforce a maximum one-hour event lifetime and five minutes for waiting prompts,
or the host's shorter request expiry. Suppress disabled preferences and the
device's fresh visible-chat lease. Bound queued events and retained receipts.
On temporary APNs rejection, retry durably with bounded backoff until expiry.
Handle token invalidation. An unknown network-send outcome is explicit and
must not be described as exactly-once delivery.

### Cancel a waiting request

`POST /v1/installations/{installation_id}/cancellations`

Body: `{"v":1,"request_id":"opaque request hex","expires_at":1800000300}`.
Persist cancellation before acknowledging; reject later deliveries for that
request until its expiry. Cancellation may precede an event. It affects unsent
work and does not recall messages already submitted to Apple.

Responses use `{"v":1,"status":"accepted"}` or a meaningful status such as
`duplicate`, `stale`, `suppressed`, `expired`, `revoked`, `cancelled`, `unknown`.
Validation/authorization/conflict/limit errors use 400/401/409/429; retryable
infrastructure failures use 503. `GET /health` is liveness, not an APNs proof.
No public endpoint lists registrations or accepts plaintext notification content.

## Encryption and APNs payload

Botto creates an independent cryptographically random AES-256 preview key per
pairing and sends it only over the existing authenticated Hermes connection.
The host stores keys with owner-only permissions. The app and notification
extension share a device-only Keychain access group with after-first-unlock
accessibility. Relay generations are not new keys by themselves.

The plaintext JSON is:

```json
{"v":1,"title":"Milo","body":"Short reply excerpt","profile_id":"profile","root_id":"root","stored_id":"stored"}
```

Use a fresh random 12-byte nonce for every encryption. `sealed` is standard
base64 of `nonce || ciphertext || 16-byte authentication tag`, matching
CryptoKit `AES.GCM.SealedBox.combined` and Python AESGCM output. The authenticated
additional data is the UTF-8 encoding of this exact newline-separated string,
with no trailing newline:

```text
botto-push:v1
<installation_id>
<device_id>
<generation as base-10 integer>
<event_id>
```

Bound plaintext to a small excerpt (at most 1,024 UTF-8 bytes for body and 160
for title); reject oversized routing IDs. The decoded combined box is at most
3,072 bytes (4,096 base64 characters), and the complete APNs JSON must fit
4,096 bytes. The complete payload budget owns deliverability: the producer
uses routing-only ciphertext when preview text exceeds it, before admission.
No attachments, tool arguments, tool results, or host URL appear
in preview payloads. Minimal routing identity stays encrypted. Authentication
failure, unknown version, missing key, extension expiry, and inaccessible
Keychain preserve the safe original alert.

The APNs payload contains `aps.alert` with title `Botto` and body `New activity`,
`mutable-content: 1`, `sound: default`, and the opaque `thread-id`. The `botto`
dictionary is:

```json
{"v":1,"installation_id":"hex","device_id":"hex","generation":1,"event_id":"hex","kind":"reply","expires_at":1800003600,"sealed":"base64"}
```

When previews are disabled, the plugin still seals the routing identity but
uses empty title/body; the extension preserves the generic alert. The relay
does not remove this routing-only ciphertext. The app reprocesses the original
encrypted envelope on tap if the extension did not finish. If no key is
available, it can open only the known host and explain that the exact
destination is unavailable. No payload may introduce a server URL,
change the saved installation, or execute an approval/reply.

## Hermes plugin interface

The authenticated host routes are under `/api/plugins/botto-push`, mounted by
Hermes from the plugin's dashboard manifest and APIRouter. The mount must retain
Hermes authentication; there is no invented `ctx.register_routes` API. Normal
plugin discovery is per Hermes profile, so enroll/install each producing profile
and preserve its authenticated profile scope.

- `GET /status` returns protocol/plugin version, verified event versions as
  `capabilities: {"native_session_events": 1}`, relay URL, installation ID, and
  device metadata without keys or bearer credentials. `supported` is true only
  when the supported observer is actually loaded and the relay is configured.
- `POST /devices` enrolls/updates the caller's random device ID with APNs token,
  environment, bundle ID, preview key (on enrollment only), preferences, and
  optional visible profile/root/stored identity. Returns the installation ID,
  device ID, authoritative generation, and preferences. Persist host state before
  relay enrollment and make retries idempotent using a caller operation UUID.
- `POST /devices/{device_id}/remove` persistently retires the target and asks the
  relay to revoke it. Report incomplete remote removal truthfully. Keep enough
  non-key removal state to retry after network recovery.
- `POST /devices/{device_id}/test` produces a host-encrypted test reply using a
  real known chat destination. Distinguish test submission from displayed proof.

The app's typed host methods must use Botto's existing authenticated HTTP session,
not create another URLSession with incomplete native credentials. Hook payload
coverage and a supported minimum Hermes version must be established from source
and a real disposable native backend before capability claims are enabled.

## Verification

The primary suite drives public relay enrollment/events/revocation/cancellation
and observes provider requests, errors, and retries. Keep Cloudflare state
adapters behind that suite. Add native entry-point and cross-language encrypted
fixtures, real supported Hermes hook tests, and signed-device end-to-end proof.
See the [notification acceptance recipe](../docs/agents/verification/features/notifications.md).
No fixture can establish an
unobserved physical-device banner or provider credential authorization.
